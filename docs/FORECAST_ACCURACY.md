## What is measured

The existing `forecast_runs` and `forecast_run_days` tables retain the original prediction. The accuracy query takes the **earliest eligible run for each service date**, ordered by generation time and run ID. A run is eligible only if it was saved before midnight at the beginning of that date in `Europe/London` and marked the day open. This prevents post-service or closed-day forecasts from appearing accurate through hindsight. Future and current service dates are excluded.

Booking totals in `restaurant_demand_features` are not assumed to be guests served. The restaurant has no POS integration, so a manager or supervisor manually records the actual served covers after a completed service in `service_actual_covers`. A correction requires a reason; `service_actual_corrections` retains the previous and new numbers, actor, and timestamp. A day without a recorded actual is explicitly shown as awaiting entry.

The protected `GET /api/staff-cost/accuracy?days=30|90|180` endpoint returns eligible daily comparisons, summary metrics, and weekday/forecast-lead segments. `POST /api/staff-cost/actuals` records the first actual; `PATCH /api/staff-cost/actuals/<date>` corrects one. The read uses `view_forecasts`; writes also require `manage_bookings`. Next.js forwards the authenticated cookie to Flask via the existing protected API proxy. New tables have RLS enabled and explicitly revoke `anon` and `authenticated` Data API privileges.

MAE is the average absolute difference in covers. Mean bias is forecast minus actual, so a positive number means overprediction. MAPE excludes zero-actual days to avoid division by zero; those days still count toward MAE and bias. The UI shows sample counts and the number of zero-actual days excluded from MAPE. A 14-day recent-error chart and daily comparison table expose trends, with weekday and lead-day breakdowns.

## Clearly separated demonstration data

At the user's request, a one-week illustrative sample was added to the **current** Supabase project, not a separate database. The `Real records` view remains the default and excludes runs whose model name is `accuracy_demo_fixture`; it still requires a genuine pre-service timestamp. The `Demo sample` view selects only that marker, labels every result as invented, hides unrelated real booking totals, and does not misrepresent its creation time as a pre-service prediction. The synthetic run is not made active or included in the saved-run list. The sample includes six invented served-cover values and one awaiting entry so the recording and correction controls can be exercised.

Migration `20261024083448_demo_actual_source.sql` adds a `source` marker to served-cover entries. Existing and future manager records retain the `manager` default and require a real `recorded_by` user. Seeded demo values use `source = 'demo'` and `recorded_by = NULL`, so no human is falsely credited; subsequent manager edits are attributed through the existing audit path. The one-time, idempotent [manual seed](../supabase/manual/demo_forecast_accuracy.sql) is intentionally excluded from migration replay and automatic deployment. Its forecast run is immutable, so the fixture should be treated as a persistent, clearly labelled demonstration record. Synthetic comparisons do **not** satisfy the remaining genuine-service acceptance criterion for item 21.
