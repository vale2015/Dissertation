Restaurant Forecasting System

Help independent restaurant managers plan each service using bookings, expected covers and staffing recommendations in one place.

Product brief

The primary goal of the dissertation was to forecast restaurant demand and support staffing decisions. The short project timeline made forecasting the priority. The chatbot, wider management workflows, agentic development process and research knowledge base were introduced afterwards as extensions. Their implementation is still ongoing.

MVP · Restaurant Forecasting System

Problem and users

  • Users: Independent restaurant managers planning floor, kitchen and bar staffing before service.
  • Demand uncertainty: Bookings give limited visibility into total demand, which can change with walk-ins, cancellations and party sizes.
  • Manual planning: Managers reconcile booking records, historical demand and staffing rules from different places.
  • Operational impact: Overstaffing raises labour costs. Understaffing can slow service and put pressure on the team.
  • Manager needs: Forecasts they can inspect, staffing recommendations they can explain and records they can revisit.

What the forecasting MVP delivers

  • Record bookings and use historical demand to predict covers for the next 7 or 10 days. A cover means one guest served.
  • Apply staffing rules to turn expected demand into recommended headcount.
  • Help the manager plan the team before service.

Ongoing extensions · Agentic Development and Research Knowledge Base

Following the forecasting MVP, the project expanded to explore how AI could help build the application and identify useful improvements. These extensions are still being developed and verified.

Agentic Development

  • Scope: The product manager defines the task and its acceptance criteria.
  • Implementation: The engineering lead chooses the work needed. A frontend or backend agent builds the change.
  • Review: A separate QA agent checks the result. UX, security or chatbot reviewers join when relevant.
  • Handoffs: Agents work one at a time, passing on changes, test results and remaining issues.
  • Acceptance and tracking: The product manager reviews the evidence. The improvement tracker records progress, and Trello mirrors status.

Research Knowledge Base

  • Purpose: Track new AI tools, techniques and hospitality forecasting approaches.
  • Evidence: Store findings with public source links and possible uses for RFS.
  • Publication: The research task submits findings through GitHub. GitHub Actions checks them and publishes the records and HTML review page.
  • Prioritisation: The product manager decides which findings deserve investigation or an approved backlog task.
  • Delivery: Development agents implement and test approved work.

For example, research about forecasting by service period could lead to a task to explore lunch and dinner predictions. The agents would develop and review the change against the product manager’s requirements.

How research becomes development work

As part of its ongoing expansion beyond forecasting, RFS uses external research to identify possible product improvements. A research task checks public AI and hospitality sources and submits its findings through GitHub. GitHub Actions checks the submission and publishes it to the knowledge base. The product manager reviews the evidence and decides which findings should become backlog tasks for the development agents.

For example, research about hourly restaurant forecasts could lead to an investigation into forecasting demand by service period.

  1. Research taskScans public AI and hospitality sources and submits findings as structured data in a GitHub issue.
  2. GitHub ActionsThe new issue triggers a workflow that checks who submitted it, verifies the data format and checks that the submission was prepared against the current main branch.
  3. Knowledge baseIf the checks pass, the workflow updates the research records and generates the HTML review page, then commits those outputs to the main branch.
  4. PM and agentsThe PM reviews evidence. Agents work on approved backlog items.

If validation fails, the previous published snapshot stays available. A manual issue submission successfully triggered publication. The scheduled submission is still to be verified.

How the system fits together

Why these boundaries matter

Keep business rules in one place

The dashboard and chatbot use the same Flask services and permissions. Next.js forwards authenticated requests from the server, keeping database access and provider credentials outside the browser.

Keep forecasts reviewable

The prediction model estimates demand. Explicit staffing rules turn those estimates into recommendations. Stored forecast runs and report snapshots preserve the figures a manager saw.

Keep staff changes safe

Staff account changes are reviewed and explicitly confirmed. Flask records each chat action once, so a retried request cannot write twice, and the last active manager cannot be demoted or disabled.

Keep optional services independent

Weather and event providers add context. The optional chatbot classifier helps resolve ambiguous requests. Core forecasting and reporting can operate when those services are unavailable.

RFS AI · Architecture

How the chatbot handles a manager’s request

What Qwen is and why we chose it

Qwen is a language model that helps interpret everyday wording. The project chose Qwen 3.8 through Cloudflare Workers AI using a free account for the prototype. Its role is to suggest a task from a fixed list. The app checks permissions and carries out the task.

Implemented staff workflow

Conversational registration and editing include exact-account review, private password capture, explicit confirmation and retry-safe writes. The accepted chatbot release is recorded separately from this dated demonstration prototype.

Agentic development

How I use agents to build and review RFS

I route each task to one specialist at a time, review the evidence, and use observed token usage to improve later handoffs.

  • Fresh role packets are capped at 500 words and handoffs at 200 words. They include the task ID, actual preceding agent, changed files, checks, gaps and next action.
  • Small, tested Node tools support the coordinator: tools/agent_workflow/packet.mjs builds the bounded task packet; labels.mjs, epics.mjs and status.mjs keep Trello labels, epic groups and list names consistent; and tools/workflow_usage/capture.mjs records usage at each handoff.
  • Every delivery tier uses a separate reviewer. One workflow and one specialist are active at a time; after two unsuccessful fix/retest cycles on the same defect, record the blocker.

Development measurement

Token usage by workflow

Each workflow gets a private ledger entry. At handoffs, the coordinator updates it and uses the analyst’s findings to identify changes worth testing.

What the ledger records

  • Measurement window. The collector follows the root chat and its descendants within an explicit UTC window. It deduplicates thread and response IDs, reads per-response usage and reports coverage through the capture time.
  • Token counts by model. The ledger records input, cached input, uncached input, output, reasoning and total. Cached input is part of input and reasoning is part of output. Total equals input plus output. Missing values are recorded as null.
  • One entry per workflow. Each entry records its stable ID, window, category and measurement state. Refreshes update that entry in place, including the analyst’s overhead. The history rejects captures that could count shared-thread usage twice.

What the analyst flags

The analyst receives sanitized counters, relevant history and flags only. It returns up to three prioritized findings with evidence, an action and a success check. Its authority is limited to review and recommendations. Implementation and acceptance stay with the delivery team and PM.

  • High average input. At least 50,000 input tokens per response across at least ten responses.
  • Coordinator input share. At least 60% of recorded input and at least 250,000 input tokens from the root chat.
  • Above comparable baseline. A full, closed, observed workflow uses over 1.5 times the median total of at least three prior full, closed, observed workflows with the same category and selection type.

These thresholds identify candidates for review. The recorded counts support comparisons of observed usage. Billing and savings claims require separate evidence.

Private history and reviews

The history files and analyst reviews stay in the ignored .workflow-usage/ directory in the project checkout.

  • usage-history.json stores one authoritative entry per workflow.
  • USAGE_HISTORY.md summarises workflows, models and token counts.
  • OPTIMIZATION_FLAGS.md records measured candidates, evidence, actions and success checks.
  • reviews/ holds the analyst reviews saved by the coordinator.

These routes apply to development work. The RFS chatbot keeps its separate Qwen model configuration. If a development model is unavailable, the coordinator reports it and requests an available choice.
